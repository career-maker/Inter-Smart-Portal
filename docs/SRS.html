Software Requirements Specification

Intersmart Employee Portal

Document SRS-ISS-2026-01 Version 1.0 Date 07 September 2026 Owner Team QA Status Active development

This specification describes the functional and non-functional requirements of the Inter Smart Employee Portal as currently implemented: an internal HR, attendance, leave, travel-allowance, and project-management system used by Intersmart's employees, team leads, and super administrators.

1 Introduction

1.1 Purpose

This document specifies the requirements of the Inter Smart Employee Portal, a browser-based internal application that centralizes employee records, attendance, leave and work-from-home requests, travel allowance claims, project/task management, internal communication, and HR service delivery for Intersmart. It is written from the current implementation to serve as a baseline reference for maintenance, onboarding new engineers, QA test-case design, and future feature planning.

1.2 Scope

The portal is a single web application with a Next.js frontend and a Laravel REST API backend, used exclusively by Intersmart staff (no public/customer-facing surface except the login screen and signed email action links). It covers: identity & role management, leave and WFH lifecycle, attendance (manual and biometric), travel allowance, an internal project-management suite (projects, tasks, bug tracking, Hubstaff time-tracking sync), a community/social layer with direct messaging and an AI assistant, recognition and engagement features, HR document/policy workflows, an internal helpdesk, and administrative configuration (settings, branding/customization, email routing, storage retention, audit logging).

1.4 Intended Audience

Team QA (the maintaining developer team), new engineers onboarding onto the codebase, and Intersmart stakeholders evaluating portal capability. Familiarity with standard web/HR-software terminology is assumed; no prior codebase knowledge is required.

2 Overall Description

2.1 Product Perspective

The portal is a self-contained internal system, not an extension of an existing product. It consists of a Next.js single-page-style application (App Router) that consumes a versionless Laravel JSON REST API over HTTPS, authenticated with Sanctum bearer tokens. All persistent data lives in a single PostgreSQL database. Outbound email (approval notifications, signed one-click approve/reject links) and an inbound biometric-device ingestion endpoint are the system's only external touchpoints besides the browser.

2.2 User Classes & Characteristics

RoleWhoCharacteristic access
Super Admin System owner / senior management Full access to every module: employee & team CRUD, all approvals, leave balance overrides, settings, customization, audit logs, reports, chat moderation. Cannot apply for leave/WFH/TA on their own account.
Team Lead Department/team leads Own profile and requests, first-level approval for their team's leave/WFH, team task & project visibility, Hubstaff view.
Employee General staff Own profile, attendance, leave/WFH/TA applications, assigned tasks, community participation, helpdesk tickets.

Roles are managed with Spatie Laravel-Permission. Only three roles are seeded and in active use — Super Admin, Team Lead, Employee. Most controllers gate by role name directly (hasRole()) rather than granular permissions, except the Project Management module, which layers its own capability checks (PmAddon / CustomTeamPermission) on top of role, so a team can be granted or denied individual PM add-ons independently of the three base roles.

A fourth role name, HR, is referenced throughout the controller layer (leave/WFH final approval, team management, announcements, holidays) as if it carried Super-Admin-adjacent authority, but it is never created by RolesAndPermissionsSeeder and is not assigned to any account. Functionally this is dead/reserved code today — every one of those hasRole('HR') checks currently resolves false, so those code paths behave as Super-Admin-only in practice. Flagged here for the dev team rather than silently omitted.

2.4 Design & Implementation Constraints

  • Authorization is enforced with inline role/ownership checks inside controllers — there is no Laravel Policy layer or fine-grained permission: route middleware outside the PM module's add-on system.
  • Queue driver is synchronous (no Redis/worker) — all "background" work (email sends, notification fan-out) executes inline in the request cycle.
  • File uploads (profile photos, bill receipts, issue attachments, chat/community attachments) are stored on local disk under storage/app/public and served via a symlink — there is no S3/object storage layer.
  • The frontend enforces route protection and role-based nav visibility client-side (middleware.ts, layout.tsx); the API independently re-enforces every rule server-side.

2.5 Assumptions & Dependencies

  • Every user has exactly one of the three roles at a time; multi-role assignment is not a designed workflow.
  • Outbound email depends on SMTP credentials configured per-tenant via the Email & SMTP Management add-on; without them, approval notifications are silently skipped.
  • Biometric attendance capture depends on an external device agent pushing events to the ingestion endpoint with a shared secret — the portal does not talk to biometric hardware directly.
  • Hubstaff time-tracking figures depend on a valid Hubstaff API token stored per project (ProjectHubstaffToken).

3 System Architecture

A conventional two-tier SPA-over-REST architecture: the browser talks only to the Next.js frontend, which in turn calls the Laravel API over NEXT_PUBLIC_API_URL. There is no server-side session — every request after login carries a Sanctum bearer token issued at login and held in the Zustand auth store.

4 Functional Requirements

Grouped by module. Each feature block lists its business rules and the primary screen(s) that implement it. Role chips show who can use the feature; a screen restricted further than its module is noted inline.

4.1 Authentication & Session

FR-AUTH-1Login, logout, password reset
PublicAll roles

Email + password login issues a Sanctum token; logout revokes it. Forgot-password sends a reset email; reset-password consumes the token and sets a new password. No self-registration — accounts are provisioned by Super Admin.

Screens: /login, /forgot-password, /reset-password

4.2 Dashboard

FR-DASH-1Role-specific landing dashboard
All roles

Single dashboard endpoint returns a different payload shape per role: KPI tiles (headcount, pending approvals, today's attendance), welcome card with computed tenure ("You have been with Intersmart for X Years Y Months Z Days"), attendance widget, today's birthdays, company updates feed, and a recent-activity stream.

Screens: /dashboard, /activities

  • Bulk import via CSV with a downloadable sample template.
  • Company-wide searchable employee directory and a public (limited-field) profile view for any authenticated user.
Screens: /employees, /employees/create, /employees/[id]
FR-EMP-2Self-service profile & change requests
All roles

Employees edit non-sensitive profile fields directly; sensitive fields go through a Profile Update Request that Super Admin must approve or reject before it applies.

4.4 Teams / Departments

FR-TEAM-1Department CRUD & membership
Super Admin
  • Team code auto-generated from the name (e.g. "Quality Assurance" → QUAL-3847) with uniqueness retry.
  • Assign/replace a Team Lead per team; sync member rosters.
  • Team list is readable by every authenticated user (for filters/switchers) but only mutable by Super Admin.
Screens: /teams, /teams/create, /teams/[id]

4.5 Leave Management

FR-LV-1Apply for leave
EmployeeTeam Lead
  • Casual Leave requires ≥3 days advance notice (backend-enforced).
  • Half-day CL/SL variants and standard full-day types are selectable leave types.
  • A day-count calculator previews consumed balance before submission.
Screens: /leaves/apply
FR-LV-2Two-stage approval workflow
Team LeadSuper Admin

Request carries independent tl_status and admin_status. Team Lead approves/rejects first; Super Admin gives final approval. If an employee has no Team Lead assigned, the request routes directly to Super Admin, skipping the TL stage.

Screens: /leaves/approvals
FR-LV-3Cancellation, override & LOP conversion
Super Admin

Employees can cancel their own pending request. Super Admin can override a decision after the fact, or convert an approved leave to Loss-of-Pay with employee confirmation/rejection of the conversion.

Screens: /leaves, /manage-leaves
FR-LV-4Leave balances & carry-forward
Super Admin
  • 12 CL + 12 SL allocated automatically every 1 January (leave:annual-allocation artisan command, also manually triggerable).
  • Unused CL carries forward for exactly one year, then expires; unused SL always expires 31 December (no carry-forward).
  • Consumption order: carry-forward balance first, then current-year allocation.
  • Every manual balance adjustment is written to a Leave Balance Audit Log with before/after values and the admin who made the change.
Screens: /leave-balances

4.6 Leave Policy Management (Add-on)

FR-LP-1Configurable accrual policy engine
Super Admin

A newer, more granular layer above the base leave-balance system: a configurable monthly accrual cycle (start-day setting), a probation period (in months) before leave accrual begins per employee, per-employee overrides and manual probation clearance, a settable CL carry-forward window in years, an SL carry-forward toggle, manual balance adjustment, and a full accrual ledger per employee. A manual "trigger cycle" action re-runs accrual outside the schedule.

Screens: /project-management/addons/leave-policy

4.7 Work From Home

FR-WFH-1WFH request, approval & cancellation
All roles

Mirrors the leave workflow: full-day/half-day WFH types, two-stage TL → Admin approval, cancellation of own pending requests, and Super-Admin-only "mark WFH on behalf of employee" for missed submissions. Same-day WFH requests are blocked for non-admin roles.

Screens: /wfh, approvals inside /leaves/approvals?tab=wfh

4.8 Attendance & Biometric Integration

FR-ATT-1Manual check-in / check-out / break tracking
All roles

Employees self-track check-in, check-out, and break start/end from the dashboard widget; the day's running status and a personal history table are available.

Screens: /attendance, /attendance/details
FR-ATT-2Biometric device ingestion
Device agent (shared-secret)

An external biometric-device agent pushes raw punch events to POST /v1/biometric/ingest, authenticated by a dedicated middleware (not Sanctum). Events are reconciled into daily attendance records, with a timezone-correction maintenance command available for historical fixes.

Admin screen: /attendance/management

4.9 Travel Allowance

FR-TA-1Apply, itemize & track TA claims
EmployeeTeam Lead

A claim has one or more expense line items (category: Travel/Food/Accommodation/Other, amount, description) plus an optional bill/receipt upload. Status lifecycle: Applied → Approved/Rejected → Paid/Unpaid. Own claims can be cancelled while still Applied.

Screens: /ta/apply, /ta/status
FR-TA-2TA approval, override & payment marking
Super Admin

On submission, HR@intersmart.in and Ameesha@intersmart.in receive an email with the claim details and one-click, signed Approve/Reject links that deep-link into the management screen and pre-expand the request for confirmation.

Screens: /ta/management

5 User Interface Requirements

5.1 Visual Design System

  • Theme: dark slate gradient background (from-slate-900 via-slate-800 to-slate-900) across every authenticated page.
  • Surfaces: glass-morphic cards — bg-white/5, backdrop-blur-md, border-white/10, rounded-2xl.
  • Accent: amber/gold (text-amber-400 / bg-amber-500) — used for header icons, primary actions, and active nav state; plain text-primary is avoided as it is invisible on the dark background.
  • Typography: Inter, via Google Fonts.
  • Iconography: Lucide React throughout.
  • Layout shell: universal hamburger navigation with role-filtered groups, auto-generated breadcrumbs from the URL path, and enforced overflow-x:hidden to eliminate horizontal scroll on any viewport.

5.4 Responsive & Accessibility Requirements

  • Fully responsive from mobile to desktop; hamburger nav collapses on small viewports; no horizontal scroll is permitted on any breakpoint.

  • Breadcrumbs on every page for wayfinding, auto-derived from the URL segment path.
  • Header icons use amber (not the default primary token) to remain visible against the dark theme.

7 External Interfaces

7.1 Email Notifications

SMTP is configured per the Email & SMTP Management add-on, with routing rules and per-employee overrides. Leave, WFH, and TA approval emails embed Laravel signed URLs (email-approve / email-reject) that let an approver act with one click without logging in first — the signed link redirects to the relevant management screen (FRONTEND_URL, defaulting to http://localhost:3000), which then prompts the logged-in admin to confirm the action with optional notes.

7.2 Biometric Device Ingestion

POST /v1/biometric/ingest accepts punch events from an external device agent, authenticated by a dedicated shared-secret middleware (VerifyBiometricAgent) rather than user login — this is a machine-to-machine interface.

7.3 Hubstaff Integration

Per-project Hubstaff API tokens authorize pulling project/user lists and time-tracking analytics into the PM module, and linking Hubstaff users to portal employee accounts.

7.4 Scheduler Webhook

POST /api/system/scheduler/run is a bearer-secret-protected endpoint that invokes Laravel's schedule:run — a workaround for the cPanel host not exposing a native cron-to-artisan hook, meant to be called by an external cron pinger.

7.5 External Team Tracker Link

The Team Lead navigation includes an outbound link to a separate hosted tool (qa-tracker-pro.vercel.app) — not part of this codebase, but part of the Team Lead's day-to-day toolchain.

8 Non-Functional Requirements

CategoryRequirement
SecurityToken-based auth (Sanctum) on every non-public route; role checks re-validated server-side on every request; signed, time-limited URLs for unauthenticated email actions; a dedicated shared-secret middleware gates the biometric and scheduler webhooks.
AvailabilitySingle-region deployment (Vercel + cPanel); no documented HA/failover — acceptable for an internal tool with business-hours usage.
PerformanceSynchronous request/response for all operations, including email sends, since no queue worker runs in production — approval actions should complete without perceptible delay for typical SMTP round-trips.
UsabilitySingle consistent dark-theme design system across 45+ screens; role-aware navigation avoids exposing controls a user cannot act on.
AuditabilityLeave balance changes and other sensitive admin actions are logged with actor, timestamp, and before/after state.
MaintainabilityController-per-resource REST structure; Eloquent models mirror the schema 1:1; PM module explicitly isolated/additive to avoid regressing the core HR routes.
Data integritySoft deletes on Users, Teams, and TA requests preserve history instead of hard-deleting; foreign keys enforce referential integrity in PostgreSQL.
